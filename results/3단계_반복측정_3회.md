## 확정 1 — 조회를 트랜잭션 밖으로 뺀 것은 효과가 없다

| | 3회 값 |
|---|---|
| V1 (조회 TX 안) | 38 / 43 / 49 |
| V2 (조회 TX 밖) | 43 / 45 / 48 |

**완전히 중첩된다.** V2 가 오히려 중앙값이 높다.
쓰기 왕복은 그대로 남으므로 조회 위치는 락 보유 시간에 거의 기여하지 않는다.

이 결론은 인덱스 문제(아래)와 무관하다 — V1 과 V2 는 **읽기 위치만 다르고 쓰기 패턴이 같기 때문**이다.

## 확정 2 — FK 는 필요조건이다

V8 3회 전부 0. 배치가 계정 행을 잠글 경로가 FK 하나뿐이므로 떼면 사이클이 성립하지 않는다.

---

## 발견 — V5 가 뒤집힌 진짜 이유는 격리수준이 아니라 **누락된 인덱스**다

1차에서 43 이던 V5 가 3회 전부 0 이 됐다. 격리수준을 배치 트랜잭션에도 걸었기 때문인데,
**왜 그렇게 큰 차이가 나는지** 확인해 보니 스키마 결함이 있었다.

```sql
EXPLAIN UPDATE notification SET status='SENT' WHERE request_id = 1;

type = index      possible_keys = NULL      key = PRIMARY      rows = 3861
```

`notification.request_id` 에 **인덱스가 없다.** 인덱스는 PK 와 `account_id` 둘뿐이다.
그래서 한 건을 갱신하는 UPDATE 가 **테이블 전체 3861 행을 스캔**한다.

- **REPEATABLE READ**: 스캔한 행 전부에 next-key 락이 걸린다 → 배치가 알림 테이블을 사실상 통째로 잠근다
- **READ COMMITTED**: 조건에 안 맞는 행의 락을 즉시 해제한다 → 락 풋프린트가 극적으로 줄어든다

**V5=0 은 "격리수준을 낮추면 데드락이 없어진다"가 아니라
"인덱스가 없어서 부풀려진 락 범위가 RC 에서 걷힌 것"이다.**

### 이건 실험의 결함이자, 동시에 건질 소재다

- **결함**: 운영 코드라면 `request_id` 에 인덱스가 있거나 PK 로 갱신했을 것이다.
  지금 baseline(40 내외)은 **누락 인덱스로 부풀려진 값**이다
- **소재**: *"인덱스 없는 컬럼으로 UPDATE 하면 단일 행 갱신이 테이블 전역 락이 된다"* 는
  실무에서 자주 나오는 사고다. 이력서의 리마인더 인덱스 재설계 경험과도 이어진다
