## 결론

**인덱스가 정상이면 11개 구성 33회가 전부 0.** 인덱스만 빼면 34~46.

`UPDATE notification SET status='SENT' WHERE request_id = ?` 가
인덱스 없이는 `rows=3861` 풀스캔이고, REPEATABLE READ 에서 스캔한 행 전부에 next-key 락이 걸린다.
한 건 갱신이 테이블 전역 락이 된다. 인덱스를 붙이면 `rows=1`.

부수적으로 배치 처리 시간도 11.8s → 6.1~9.0s 로 줄었다.

## 앞선 결론들의 운명

| 결론 | 상태 |
|---|---|
| 조회를 TX 밖으로 = 효과 없음 | **유지** — 결함 스키마에서도 V1(38/43/49) vs V2(43/45/48) 완전 중첩. 두 구성은 읽기 위치만 다르고 쓰기 패턴이 같아 인덱스와 무관 |
| FK 가 필요조건 | **약화** — 원문으로 확인한 경로는 사실이나, 인덱스가 정상이면 그 경로만으로는 이 부하에서 사이클이 안 생겼다 |
| 왕복 횟수가 지배항 | **폐기** — 결함 스키마 한정 관찰이었다 |
| V5(RC) = 0 | **재해석** — 격리수준 효과가 아니라 누락 인덱스가 만든 락 범위가 RC 에서 걷힌 것 |

## 이력서 판단 — 아직 보류

말할 수 있는 것: *"동일 구조를 실험 환경에서 재현했을 때 락 범위가 지배적이었고, 조회 위치나 chunk 전환은 차이를 만들지 않았다."*

말할 수 없는 것: *"운영 데드락의 원인도 인덱스였다."* 회사 스키마를 확인하지 않았다.

**확인 필요**: 운영에서 그 UPDATE 가 인덱스를 탔는가?
- 안 탔다면 → 세 조치는 증상을 다루고 있었을 수 있다. 이력서의 "근본 조치" 재작성
- 탔다면 → 실험 결과는 실험 환경 한정으로 남기고 운영 서술 유지
