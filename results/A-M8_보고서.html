인덱스 하나가 만든 데드락

푸시 발송 데드락의 원인을 가리려고 모델을 세 번 폐기하고 36회를 측정했다. 원인은 측정 대상 바깥에 있었다.

8단계 추적 3회 모델 폐기 36회 최종 측정 MySQL 8.0 · 2 CPU / 2 GB

증상

운영 중인 알림 서버에서 푸시 발송 데드락이 주 2~3회 발생했다. 발송 대상은 평균 1천 명 규모. 죽는 쪽은 배치가 아니라 사용자 요청이었다.

장애 대응이 우선이라 조치 세 가지를 한 번에 넣었고 0건이 됐다. 그래서 무엇이 실제로 효과가 있었는지 모른다.

조치 ①
대상 조회를 트랜잭션 밖으로 분리
조치 ②
상태 갱신을 BATCH UPDATE 로 전환
탐색 과정
처리 청크 500 → 200 축소 (조치가 아니라 원인을 좁히는 과정이었다)

운영 시스템에서 데드락을 일부러 낼 수는 없다. 같은 구조를 실험 환경에 세우고 조치를 하나씩만 되돌려 기여도를 가르기로 했다.

결론부터 — 조치 셋 다 아니었다. notification.request_id에 인덱스가 없던 것이 원인이었다.

인덱스가 정상이면 12개 구성 중 11개가 데드락 0건이다. 인덱스 하나를 빼면 그 자리에서 34~46건이 난다. 아래는 거기까지 간 기록이다.

추적 기록

가설 기각

배치 워커끼리 부딪히는 것 아닐까

같은 테이블의 같은 행들을 워커마다 다른 순서로 잡으면 사이클이 생긴다. 8워커에 처리 순서를 섞어 넣었다.

결과
데드락률 85%, 3회 안정 재현
기각 사유
실제 사건은 배치와 수신자의 충돌이었다. 이 모델에는 사용자 워크로드가 아예 없다
배운 것
재현됐다고 맞는 모델은 아니다. 숫자가 크게 나오면 오히려 의심해야 했다
측정 불가

배치와 수신자를 한 프로세스에서 흉내내다

배치 스레드와 수신자 스레드를 한 JVM에 두고 돌렸다. 수신자 실패가 잡히기는 했는데, 그게 데드락인지 알 수 없었다.

문제
HikariCP 풀 하나를 양쪽이 공유한다. 배치가 커넥션을 오래 쥐면 수신자는 커넥션을 못 얻어서 실패한다 — 데드락이 아니라 풀 고갈이다
조치
서버를 셋으로 분리. 요청·수신자는 Node(mysql2), 배치는 JVM. 런타임까지 갈라서 풀·GC·스레드 모델을 물리적으로 분리했다
계측 오류

데드락 137건이 전부 “락 타임아웃”으로 집계됐다

앱은 데드락 0건이라는데 INNODB_METRICS는 137을 가리켰다. 숫자가 정확히 일치해서 오분류임이 드러났다.

원인
Spring 예외 타입에 기댔다. 1213(데드락)과 1205(락 타임아웃)이 둘 다 PessimisticLockingFailureException 하위라 타입만으로는 갈리지 않는다
조치
예외 사슬에서 벤더 에러코드를 꺼내 판별. Node 쪽은 err.errno. 이후 InnoDB 카운터와 앱 집계를 매회 교차 검증했다
남는 값
계측을 먼저 검증하지 않았으면 이 뒤의 측정이 전부 무의미했다
재현 성공

수신자만 죽는다 — 그리고 FK가 보였다

서버를 나누고 계측을 고치자 사건이 재현됐다. 데드락 46 / 45 / 48건, 3회 안정. 배치 롤백은 0이다.

victim
언제나 수신자. InnoDB는 undo가 적은 쪽을 죽인다 — 배치는 undo 1,384 / 수신자는 1
피해
배치는 재시도하면 그만이지만 수신자는 로그인과 알림 확인이 실패한다. 화면에서 에러를 본다
발견
원문에 lock mode S locks rec but not gap waiting. 배치 코드에 계정 테이블을 잠그는 문장이 한 줄도 없는데 FK 검사가 잠그고 있었다
*** (1) TRANSACTION:          ← 수신자
UPDATE notification SET read_at = NOW(6) WHERE id = 962
*** (1) HOLDS THE LOCK(S):
  table `member_account`  lock_mode X  ... asc tk-781967862 ;;   토큰 갱신이 잡은 락
*** (1) WAITING FOR THIS LOCK TO BE GRANTED:
  table `notification`     lock_mode X waiting

*** (2) TRANSACTION:          ← 배치 · undo 1384, row lock 5368
INSERT INTO notification (account_id, request_id, status, created_at)
       VALUES (962, 3962, 'CREATED', NOW(6))
*** (2) HOLDS THE LOCK(S):
  table `notification`     lock_mode X
*** (2) WAITING FOR THIS LOCK TO BE GRANTED:
  table `member_account`  lock mode S locks rec but not gap waiting   ← FK가 요구한 락

*** WE ROLL BACK TRANSACTION (1)
1차 측정

조치를 하나씩 되돌려 보니 조회 분리는 효과가 없었다

운영에서 밟은 순서를 그대로 변수로 만들었다. ① Tasklet → ② chunk 전환 → ③ 조회를 트랜잭션 밖으로 → ④ 발송 방식 변경 세 가지.

재현 확인
V0 Tasklet 45 → V1 chunk 전환 35. chunk로 바꿔도 안 없어진다 — 운영에서 겪은 것과 같다
이상 신호
V2(조회를 TX 밖으로) 40. 이력서가 “근본 조치”라 부르는 것이 baseline과 구분되지 않는다
효과 있음
V3a(벌크로 묶기) 0, V3b(알림 선생성) 0, V8(FK 제거) 0
주의
V0가 실행마다 33~48로 흔들린다. 33~48은 노이즈 범위라 그 안의 값들은 서로 갈리지 않는다

여기서 결론을 냈다 — “락 보유 시간은 왕복 횟수가 지배한다”. V3c는 인위적 지연을 전부 뺐는데도 36건이 났고, 왕복만 3회로 줄인 V3a는 0이었기 때문이다. 이 결론은 뒤에 폐기된다.

원인 발견

V5가 뒤집혔다 — 격리수준이 아니라 인덱스였다

1차에서 놓친 결함 하나를 고쳤다. V5(READ COMMITTED)의 격리수준이 수신자에만 걸리고 배치 트랜잭션에는 안 걸려 있었다. 양쪽에 걸고 다시 재니 43 → 0으로 뒤집혔다.

격리수준 하나로 40건이 0이 되는 건 과하다. EXPLAIN을 떠봤다.

EXPLAIN UPDATE notification SET status='SENT' WHERE request_id = 1;

type=index   possible_keys=NULL   key=PRIMARY   rows=3861
결함
notification.request_id에 인덱스가 없다. 한 건을 고치는 UPDATE가 테이블 3,861행을 훑는다
왜 락이 되나
REPEATABLE READ는 스캔한 행 전부에 next-key 락을 건다. 단일 행 갱신이 사실상 테이블 전역 락이 된다. READ COMMITTED는 안 맞는 행을 즉시 풀어준다 — 그래서 V5가 0이 됐던 것이다
판정
V5=0은 격리수준 효과가 아니었다. 인덱스 누락으로 부풀려진 락 범위가 걷힌 것이다. baseline 40 내외도 부풀려진 값이다
변수로 승격

결함을 지우지 않고 측정 대상으로 만들었다

인덱스를 추가하고 끝낼 수도 있었지만, 인덱스 유무 자체를 노브로 분리했다. 그래야 “인덱스 하나 빠뜨리면 데드락이 몇 배가 되는가”가 숫자로 남는다.

추가
ALTER TABLE notification ADD INDEX idx_noti_request (request_id) → rows=3861이 rows=1로
신규 변수
V10 — 다른 조건은 V1과 같고 인덱스만 없는 구성
원인 확정

인덱스가 있으면 무엇을 해도 0, 없으면 무엇을 해도 난다

12개 구성을 3회씩 36회 돌렸다.

인덱스 정상 0 11개 구성 × 3회 = 33회 전부
인덱스 없음 · V10 34~46 3회 · 중앙 42
배치 처리 시간 −30% 11.8s → 6.1~9.0s

Tasklet이냐 chunk냐, 조회를 밖으로 뺐냐, 벌크로 묶었냐, FK가 있냐 — 인덱스가 있는 한 어느 것도 차이를 만들지 않았다.

인덱스를 고치기 전에는 이렇게 보였다

같은 구성들을 결함 있는 스키마에서 재면 전혀 다른 그림이 나온다. 그때는 왕복 횟수가 지배항이라는 결론을 냈었다. 인덱스를 고치자 그 결론이 통째로 사라졌다.

결함 있는 스키마에서도 이미 한 가지는 분명했다 — V1(38/43/49)과 V2(43/45/48)가 완전히 중첩한다. 조회를 트랜잭션 밖으로 빼도 값이 내려가지 않았다. 쓰기 왕복은 그대로 남기 때문이다. 이 관찰만은 인덱스와 무관하다. 두 구성은 읽기 위치만 다르고 쓰기 패턴이 같다.

그래서 이력서는

현재 서술

주 2~3회 발생하던 푸시 알림 발송 데드락. 대상 조회와 발송 처리가 한 트랜잭션에 묶여 트랜잭션이 길어진 것이 원인. 조회를 트랜잭션 밖으로 분리해 락을 쥔 채 대기하는 구간 자체를 제거한 것이 근본 조치였고, 상태 갱신을 BATCH UPDATE로 전환해 락 점유 시간을 추가로 줄임 → 0건

말할 수 있다 동일 구조를 재현했을 때
락 범위가 지배적이었다 조회 위치도 chunk 전환도 차이를 만들지 않았다
말할 수 없다 운영 데드락의 원인도
인덱스였다 회사 스키마를 확인하지 않았다

다음 확인 하나로 갈린다. 운영에서 그 UPDATE가 인덱스를 탔는가?

안 탔다면 조치들은 증상을 다루고 있었을 수 있고, 이력서의 “근본 조치”는 다시 써야 한다. 탔다면 이 실험 결과는 실험 환경 한정으로 남기고 운영 서술은 그대로 둔다.

어느 쪽이든 새로 생긴 이야기가 있다. 데드락을 만나면 트랜잭션 길이부터 보게 되는데, 실제로 지배한 것은 락 범위였다. 실행계획을 먼저 떠보는 것이 순서였다.

남은 검증

  • 0의 의미를 확정한다 — 인덱스가 정상인 상태에서 부하를 올려 데드락이 다시 나는 지점을 찾는다. 지금의 0은 “불가능”이 아니라 “이 부하에서 재현되지 않음”이다
  • 운영 UPDATE의 실행계획 확인 — 이력서 서술 수정 여부가 여기 걸린다
  • 화면에서 재현 — 요청 서버와 수신자 서버에 대시보드를 붙여 직접 눌러 데드락을 만들고, 수신자가 보는 실패 화면을 남긴다

실험 환경의 결과이며 운영 환경의 실측이 아니다. 고정값 — MySQL 8.0 (2 CPU / 2 GB), innodb_lock_wait_timeout=5s, 테넌트 5 · 계정 1,000 · 발송요청 4,000 · 외부 API 지연 400µs, 수신자 동시 12 / 간격 3ms. 배치는 Java 21 · Spring Batch · JPA, 요청과 수신자는 Node(mysql2)로 커넥션 풀을 분리했다.
