인덱스 하나가 만든 데드락

푸시 발송 데드락을 없앤 조치들 중 무엇이 진짜였는지 가리려고 12개 구성을 3회씩 측정했다. 답은 측정 대상 바깥에 있었다.

36회 실행 12개 구성 × 3회 MySQL 8.0 · 2 CPU / 2 GB 계정 1,000 · 발송요청 4,000 수신자 동시 12
인덱스가 정상이면 12개 구성 중 11개가 데드락 0건이다. 인덱스 하나를 빼면 그 자리에서 34~46건이 난다.

Tasklet이냐 chunk냐, 조회를 트랜잭션 밖으로 뺐냐, 벌크로 묶었냐, FK가 있냐 — notification.request_id에 인덱스가 있는 한 어느 것도 차이를 만들지 않았다. 인덱스를 떼는 순간에만 데드락이 났다.

인덱스 정상 0 11개 구성 × 3회 = 33회 전부
인덱스 없음 (V10) 34~46 3회 · 중앙 42
배치 처리 시간 −30% 11.8s → 6.1~9.0s

왜 인덱스가 락 문제가 되나

배치는 발송을 끝내고 UPDATE notification SET status='SENT' WHERE request_id = ?로 한 건을 갱신한다. request_id에 인덱스가 없으면 이 문장이 테이블 전체를 훑는다.

EXPLAIN UPDATE notification SET status='SENT' WHERE request_id = 1;

인덱스 없음   type=index   possible_keys=NULL              key=PRIMARY            rows=3861
인덱스 있음   type=range   possible_keys=idx_noti_request  key=idx_noti_request   rows=1

REPEATABLE READ에서는 스캔한 행 전부에 next-key 락이 걸린다. 한 건을 고치려는 문장이 알림 테이블을 사실상 통째로 잠근다. 그 상태로 외부 채널사 응답을 기다리니, 그사이 접속한 수신자는 어느 알림을 열어도 배치와 부딪힌다.

인덱스를 붙이면 락 범위가 3,861행에서 1행으로 줄어든다. 부딪힐 확률이 사라진다.

부딪히는 순간

배치는 member_account를 갱신하는 코드가 한 줄도 없다. 그런데 알림을 INSERT할 때 FK 검사가 부모 행에 S락을 요청한다. 수신자는 로그인하면서 그 행에 X락을 쥔다.

1
배치UPDATE notification — 알림 행에 X락 (인덱스가 없으면 3,861행)
2
수신자UPDATE member_account — 토큰 갱신이 계정 행에 X락
3
배치 · 대기INSERT notification → FK가 계정 행에 S락을 요구 → 수신자가 쥐고 있음
4
수신자 · 대기UPDATE notification 읽음 처리 → 배치가 쥐고 있음
X
InnoDB사이클 감지. undo가 적은 쪽을 죽인다 — 언제나 수신자

배치는 36회 실행 내내 롤백이 0이었다. 죽는 쪽은 항상 수신자다. 배치는 재시도하면 그만이지만 수신자는 로그인이나 알림 확인이 실패한다. 화면에서 에러를 본다.

실측 원문 — SHOW ENGINE INNODB STATUS

*** (1) TRANSACTION:          ← 수신자
UPDATE notification SET read_at = NOW(6) WHERE id = 962
*** (1) HOLDS THE LOCK(S):
  table `member_account`  lock_mode X  ... asc tk-781967862 ;;   토큰 갱신이 잡은 락
*** (1) WAITING FOR THIS LOCK TO BE GRANTED:
  table `notification`     lock_mode X waiting

*** (2) TRANSACTION:          ← 배치 · undo 1384, row lock 5368
INSERT INTO notification (account_id, request_id, status, created_at)
       VALUES (962, 3962, 'CREATED', NOW(6))
*** (2) HOLDS THE LOCK(S):
  table `notification`     lock_mode X
*** (2) WAITING FOR THIS LOCK TO BE GRANTED:
  table `member_account`  lock mode S locks rec but not gap waiting   ← FK가 요구한 락

*** WE ROLL BACK TRANSACTION (1)

배치 코드에 member_account를 잠그는 문장은 없다. lock mode S는 FK 검사가 만든 것이다. 추측이 아니라 원문에 찍힌 값이다.

인덱스를 고치기 전에는 이렇게 보였다

같은 구성들을 결함 있는 스키마에서 재면 전혀 다른 그림이 나온다. 그때는 왕복 횟수가 지배항이라는 결론을 냈었다. 인덱스를 고치자 그 결론이 통째로 사라졌다.

현재 서술

주 2~3회 발생하던 푸시 알림 발송 데드락. 대상 조회와 발송 처리가 한 트랜잭션에 묶여 트랜잭션이 길어진 것이 원인. 조회를 트랜잭션 밖으로 분리해 락을 쥔 채 대기하는 구간 자체를 제거한 것이 근본 조치였고, 상태 갱신을 BATCH UPDATE로 전환해 락 점유 시간을 추가로 줄임 → 0건

이 실험이 말할 수 있는 것과 없는 것을 갈라야 한다.

말할 수 있다 동일 구조를 재현했을 때
락 범위가 지배적이었다 조회 위치도 chunk 전환도 차이를 만들지 않았다
말할 수 없다 운영 데드락의 원인도
인덱스였다 회사 스키마를 확인하지 않았다

확인이 필요하다. 운영에서 그 UPDATE가 인덱스를 탔는가? 안 탔다면 세 조치는 증상을 다루고 있었을 수 있고, 그렇다면 이력서의 근본 조치는 다시 써야 한다. 탔다면 이 실험 결과는 실험 환경 한정으로 남기고 운영 서술은 그대로 둔다.

어느 쪽이든 새로 생긴 이야기가 있다 — 데드락을 만나면 트랜잭션 길이부터 보게 되는데, 실제로 지배한 것은 락 범위였다. 실행계획을 먼저 떠보는 것이 순서였다.

틀렸던 것들

결론에 이르기까지 모델을 세 번 폐기했다. 남겨두는 이유는, 이 기록이 있어야 마지막 결론이 우연이 아니라는 근거가 되기 때문이다.

  • 초판 모델 폐기 — 데드락을 배치 워커끼리의 행 순서 충돌로 잡았다. 85%를 3회 재현했지만 실제 사건은 배치와 수신자의 충돌이었다. 사용자 워크로드가 아예 없는 모델이었다.
  • 단일 프로세스 폐기 — 커넥션 풀을 공유해서 수신자 실패가 데드락인지 풀 고갈인지 갈리지 않았다. 서버를 셋으로 나눴다.
  • 데드락 137건 오분류 — Spring 예외 타입에 기댔더니 1213과 1205가 둘 다 PessimisticLockingFailureException 하위라 전부 타임아웃으로 집계됐다. 벤더 에러코드로 바꿨다.
  • 지표 수집 레이스 — 작업 종료 후 실패가 이전 실행에 붙어 콘솔 0 · DB 2로 갈렸다. 정지 신호를 받으면 즉시 마지막 집계를 하고 닫도록 고쳤다.
  • 스키마 결함 — 그리고 이 보고서의 결론이 된 인덱스 누락. 결과가 이상해서 EXPLAIN을 떠보지 않았다면 격리수준을 낮추면 데드락이 사라진다는 틀린 결론을 낼 뻔했다.

다음

  • 인덱스가 정상인 상태에서 부하를 올려 데드락이 다시 나는 지점을 찾는다. 그래야 0의 의미가 확정된다
  • 운영 UPDATE의 실행계획 확인 — 이력서 서술 수정 여부가 여기 걸린다
  • 요청 서버와 수신자 서버에 대시보드를 붙여 화면에서 직접 재현하고 실패 화면을 남긴다

실험 환경의 결과이며 운영 환경의 실측이 아니다. 고정값 — MySQL 8.0 (2 CPU / 2 GB), innodb_lock_wait_timeout=5s, 테넌트 5 · 계정 1,000 · 발송요청 4,000 · 외부 API 지연 400µs, 수신자 동시 12 / 간격 3ms. 배치는 Java 21 · Spring Batch · JPA, 요청과 수신자는 Node(mysql2)로 커넥션 풀을 분리했다.
