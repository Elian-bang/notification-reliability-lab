## 판정 1 — 배치는 죽지 않고 수신자만 죽는다

**배치 롤백 0, 수신자 데드락 46.** 예측대로다.

InnoDB 는 undo 가 적은 쪽을 victim 으로 고른다. 원문에서:

- 배치 TX: `5368 row lock(s), undo log entries 1384`
- 수신자 TX: `2 row lock(s), undo log entries 1`

→ `*** WE ROLL BACK TRANSACTION (1)` = **수신자**

배치는 재시도하면 되지만 **수신자는 로그인·알림 확인이 실패한다.**
사용자가 화면에서 에러를 본다. 이게 이 사건의 실제 피해다.

## 판정 2 — FK 가 연결 고리라는 것이 원문에 찍혔다

```
*** (1) TRANSACTION:   ← 수신자 (172.20.0.3 = receiver 컨테이너)
UPDATE notification SET read_at = NOW(6) WHERE id = 962

*** (1) HOLDS THE LOCK(S):
RECORD LOCKS ... index PRIMARY of table `deadlock_lab`.`member_account`
  trx id 40180 lock_mode X locks rec but not gap
  ... asc tk-781967862 ...          ← 토큰 갱신이 잡은 X락

*** (1) WAITING FOR THIS LOCK TO BE GRANTED:
RECORD LOCKS ... index PRIMARY of table `deadlock_lab`.`notification`
  lock_mode X locks rec but not gap waiting


*** (2) TRANSACTION:   ← 배치
INSERT INTO notification (account_id, request_id, status, created_at)
  VALUES (962, 3962, 'CREATED', NOW(6))

*** (2) HOLDS THE LOCK(S):
RECORD LOCKS ... table `deadlock_lab`.`notification` ... lock_mode X

*** (2) WAITING FOR THIS LOCK TO BE GRANTED:
RECORD LOCKS ... index PRIMARY of table `deadlock_lab`.`member_account`
  trx id 40166 lock mode S locks rec but not gap waiting     ← FK 락

*** WE ROLL BACK TRANSACTION (1)
```

**배치 코드에는 `member_account` 를 갱신하는 문장이 한 줄도 없다.**
그런데 `INSERT INTO notification` 이 FK 검사로 부모 행에 **S락을 요청**하고 있다.
`lock mode S` 가 원문에 그대로 찍힌다.

> *"배치에는 그 테이블을 건드리는 코드가 없었습니다. FK가 잠그고 있었습니다."*
> 이 문장이 추측이 아니라 **원문 근거를 가진 주장**이 됐다.

## 겪은 실패 2건 (실패 리포트 소재)

1. **데드락 137건이 전부 "락 타임아웃"으로 잘못 집계됨** (2판)
   Spring 예외 타입에 의존한 탓. 1213과 1205가 둘 다 `PessimisticLockingFailureException`
   하위라 타입만으로는 구분이 안 된다. **벤더 에러코드로 판별하도록 수정.**
2. **`Already value ... bound to thread`** — Job 스텝에 별도 `DataSourceTransactionManager` 를
   만들어 JobRepository 의 `JpaTransactionManager` 와 충돌. 같은 TM 을 쓰도록 수정.
