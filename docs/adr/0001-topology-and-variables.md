# ADR 0001 — 데드락 토폴로지와 실험 변수

- 상태: 채택
- 맥락: A-M8 Deadlock Matrix

## 문제

운영에서 푸시 발송 데드락(주 2~3회)을 두 조치로 없앴다.

1. 발송 대상 조회를 트랜잭션 밖으로 분리
2. 상태 갱신을 BATCH UPDATE 로 전환

그리고 원인을 좁히는 **탐색 과정**에서 처리 청크를 500 → 200 으로 줄여보기도 했다.
이건 조치가 아니라 과정이었으므로 서류에서는 제외하되, **효과가 실제로 있었는지는 V2 로 확인한다.**

**둘을 한 번에 넣었다.** 장애 대응이 우선이라 통제 실험을 못 했고,
그래서 *"무엇이 실제로 효과가 있었나"* 에 답할 근거가 없다.

## 검토한 대안

| 대안 | 버린 이유 |
|---|---|
| 운영 코드에서 조치를 하나씩 되돌려 확인 | 운영 시스템에서 데드락을 일부러 내는 실험은 불가 |
| 이론 정리로 면접 답변만 보강 | "실험실에서 확인했다"와 "이론상 그렇다"는 무게가 다르다 |
| 알림 스택 전체 재현(RabbitMQ·Prometheus 포함) | 데드락은 **DB 동시성** 문제다. 메시지 브로커가 필요 없다 |
| 단일 프로세스에서 스레드로 두 워크로드 흉내 | **커넥션 풀을 공유**해서, 수신자 실패가 데드락인지 풀 고갈인지 갈리지 않는다 |

## 결정

**서버 3개로 나누고, baseline 에서 변수를 하나씩만 뗀다.**

### 토폴로지

배치 워커끼리의 충돌이 아니라 **배치 트랜잭션 ↔ 수신자 요청**으로 모델링한다.
운영에서 겪은 사건이 그 구조였다 — 배치가 알림을 발송하는 중에 고객이 알림 상세를 열었다.

수신자 경로는 **로그인/토큰 갱신 → 알림 확인** 순서다.
토큰 갱신이 `member_account` 에 X락을 걸고, 그다음 `notification` 을 건드린다.
배치는 반대로 `notification` 을 먼저 잡는다. **여기서 사이클이 생긴다.**

> 토큰 갱신을 락으로 생각하는 사람은 없다. 인증의 부수 효과일 뿐이라고 본다.
> 이 실험의 핵심 서사가 이것이다.

### FK 를 유지한다

`notification.account_id → member_account.id` FK 를 둔다.
InnoDB 는 자식 행 INSERT 시 부모 행에 S락을 걸기 때문에,
**배치가 계정을 UPDATE 하지 않아도** 수신자의 토큰 갱신과 사이클이 생긴다.
이 숨은 경로의 기여도를 재는 것이 V8 이다.

### 변수 — 한 번에 하나만

전 조합(full factorial)이 아니라 OFAT 로 간다.
질문이 *"어느 조치가 원인을 제거했나"* 라서 **단독 효과가 바로 보여야** 한다.

| # | 바꾸는 것 | 검증 |
|---|---|---|
| V0 | — (baseline) | 사건 재현 |
| V1 | 조회를 TX 밖으로 | 조건 ③ |
| V2 | chunk 200 | **탐색 과정이었나 조치였나** |
| V3 | BATCH UPDATE | 조건 ③ |
| V4 | 수신자 자원 순서 통일 | **조건 ② 제거** |
| V5 | READ COMMITTED | 조건 ① |
| V6 | V1+V3 | **운영 적용 조합** |
| V8 | FK 제거 | **조건 ④ 제거** |

### JdbcTemplate 이 아니라 JPA 를 쓴다

초판은 락 동작을 정확히 통제하려고 JdbcTemplate 을 골랐다.
**바꾼다.** 운영 스택이 JPA 이고, JPA 의 flush 순서 문제 자체가
이 실험에서 건질 발견이기 때문이다.

대신 자원 순서를 통제하기 위해 **명시적 `em.flush()` 또는 JPQL bulk update** 를 쓴다.
이걸 안 하면 코드에 A→B 라고 써도 락은 B→A 로 잡힐 수 있다.

## 결과

- 조치별 기여도를 실측으로 분리할 수 있다
- `SHOW ENGINE INNODB STATUS` 로 **락 순서와 victim** 을 직접 확인한다
- 가설이 맞으면(V1·V3 가 둘 다 완화책이면) 이력서의
  *"조회를 트랜잭션 밖으로 = 근본 조치"* 서술을 고쳐야 한다

## 대가

- 서버 3개 + 이종 런타임이라 셋업 비용이 크다
- 실험 환경의 결과이지 운영 환경의 실측이 아니다.
  서술은 *"동일 구조를 실험 환경에서 재현해 확인했다"* 로 한정한다

## 기록해 둘 실패

**2판 첫 실행에서 데드락 137건이 전부 "락 타임아웃"으로 잘못 집계됐다.**
Spring 의 예외 타입에 의존한 탓이다 — 1213(데드락)과 1205(락 타임아웃)이
둘 다 `PessimisticLockingFailureException` 하위라 타입만으로는 구분되지 않는다.
**벤더 에러코드로 판별하도록 고쳤다.** Node 쪽은 `err.errno` 로 본다.
